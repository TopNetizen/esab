# 技能创建指南（Skill Creator）

技能（skill）是模块化、自包含的文件夹，通过提供专门知识、工作流和工具扩展桥接器的能力——把通用智能体变成掌握特定领域程序化知识的专业助手。技能可以提供：

1. **专门工作流**：特定领域的多步骤流程。
2. **工具集成**：操作特定软件、文件格式或 API 的方法与说明。
3. **领域专业知识**：企业或项目特有的知识、数据结构、业务约定。
4. **随附资源**：供复杂或重复性工作使用的脚本、参考文档、模板资产。

## 核心原则

### 精炼至关重要

上下文窗口是公共资源，技能要与系统提示、对话历史、其他技能的元数据和用户请求共享它。**默认前提：模型已经非常聪明，只补充它不知道的内容。**审视每一段：

- 「模型真的需要这段解释吗？」
- 「这段的价值配得上它消耗的 token 吗？」

优先给精炼的示例，而非冗长的解释。

### 设定适当的自由度

指令的具体程度与任务的脆弱性、可变性匹配：

- **高自由度（纯文字指引）**：多种做法都有效、决策依赖上下文时。
- **中自由度（伪代码或带参数的脚本）**：有推荐模式、允许一定变化时。
- **低自由度（具体脚本、参数极少）**：操作脆弱易错、必须保证一致性或顺序时。工程软件的 COM/API 调用序列多属此类。

把执行技能的模型想成在走一条路径：两侧是悬崖的窄桥需要明确护栏（低自由度），开阔的田野容许多条路线（高自由度）。

### 验证独立于创建过程

对技能的验证不能靠创建时留在上下文里的信息兜底：

- 新写的脚本必须实际运行确认，不能只靠目测。
- 技能整体效果要在**新会话**中以自然的用户请求实测（见「技能测试」）。
- 测试只提供原始材料（任务说法、输入文件），不附带预期答案、怀疑的缺陷或拟定修复——否则测到的是泄露的上下文，不是技能本身。

## 技能的结构

每个技能由必需的 SKILL.md 和可选的随附资源组成：

```text
skill-name/
├── SKILL.md         （必需：YAML frontmatter + Markdown 正文）
├── scripts/         （可选：可执行脚本）
├── references/      （可选：按需加载进上下文的参考文档）
└── assets/          （可选：不进上下文、供产出使用的文件）
```

### SKILL.md（必需）

- **frontmatter**：`name` 与 `description`，是判断「何时使用该技能」的**唯一依据**（常驻系统提示）。description 须同时写清技能做什么、什么情况下触发；所有「何时使用」的信息都放这里，不要放正文——正文触发后才会被读到。
- **可选元数据**：预览版使用 `metadata: { beta: true }`（YAML 布尔值），在 Skills 页面显示 Beta、默认关闭，用户确认后开启；未标记时按稳定版处理。`license` 写适用的许可声明，已有声明应保留，它不参与运行时解析或授权档位判断。
- **正文**：触发后经 `use_skill` 加载，写具体工作流、规则与示例。

### scripts/ —— 可执行脚本

同一段代码会被反复重写、或需要确定性可靠性时，沉淀为脚本。

- 运行方式：`use_skill('<技能名>', run='scripts/xxx.py', run_args='<参数>')`。脚本以**独立子进程**运行：工作目录为当前会话 workspace，虚拟环境与 esab_shim 包可用。
- **子进程没有持久命名空间**：需要分步交互、保留变量或占用 COM 连接（PKPM/Excel 等）的逻辑不要做成脚本，应在 SKILL.md 里写成代码段，指导用 `python_executor` 执行（其命名空间在会话内持久）。
- 好处：省 token、行为确定、不读入上下文即可执行；必要时模型仍可读脚本内容做修补。

### references/ —— 参考文档

工作时需要查阅的材料：API 速查、数据结构、规范细节、详细工作流。

- 读取方式：`use_skill('<技能名>', file='references/xxx.md')`；技能内引用参考文档时按此写法给出。
- 好处：SKILL.md 保持精炼，细节仅在需要时加载。
- 超过 100 行的参考文件顶部放目录；万词级的大文件在 SKILL.md 里给出检索关键词。
- **避免重复**：一项信息只存在于 SKILL.md 或某个参考文件之一。除非内容是技能的核心流程，详细材料一律放 references/。

### assets/ —— 资产文件

不读入上下文、而是用在最终产出里的文件：文档/表格模板、图片、图标、样板工程、字体等。

### 不应纳入技能的内容

技能只放智能体完成任务所需的信息。**不要**创建 README.md、INSTALLATION_GUIDE.md、QUICK_REFERENCE.md、CHANGELOG.md 之类的辅助文件——创建过程、安装测试步骤、面向人的说明只会增加杂乱。

##桥接器环境要点

- **存放位置**：新技能一律创建到用户技能目录 `%LOCALAPPDATA%\esab\skills`（init_skill.py 的默认输出位置）。技能根目录共三类，优先级为 内置技能 > SKILLS_EXTRA_PATHS（.env 配置的第三方路径）> 用户技能目录；不在这三类之下的目录不会被系统发现。
- **重名会被遮蔽**：同名技能按上述优先级取高者。创建前先对照系统提示中的「可用技能清单」确认名字不冲突；想定制某个内置技能的行为，做法是**换名**新建用户技能，而不是建同名技能。
- **内置技能勿改**：内置技能随包明文分发，改动会在升级时丢失；可用 `use_skill` 读取它们参考写法。
- **编码铁律**：技能内所有文本文件必须 UTF-8 且**无 BOM**。BOM 会让 frontmatter 解析失败、技能从清单中消失；GBK 写盘会乱码。用 python_executor 写文件时显式 `encoding="utf-8"`。
- **面向桥接器编写**：技能是写给另一个桥接器实例的，内容围绕它的工具集组织——`python_executor`（核心抓手）、`shell_executor`、`ask_user_question`、`use_skill`。涉及工程量的技能遵守单位约定：长度 mm、力 kN、质量 t。
- **生效时机**：文件落盘即生效——技能清单每次模型调用前刷新，`use_skill` 按名即时可用，无需重启。

## 渐进式披露

技能按三级加载，高效使用上下文：

1. **元数据（name + description）**：常驻系统提示（约百字）。
2. **SKILL.md 正文**：触发后加载（控制在 500 行以内）。
3. **随附资源**：按需加载；脚本可不读入上下文直接执行，规模基本不受限。

正文接近 500 行时把内容拆到 references/，并在 SKILL.md 里注明**何时**读哪个文件。技能覆盖多种变体/软件/场景时，SKILL.md 只留核心工作流与选择指引，变体细节全部下沉到参考文件。三种组织模式：

**模式 1：高层指南 + 引用文件**。SKILL.md 写快速上手，进阶内容指向单独文件。内置技能 excel-link 即此模式：正文只做任务路由（读取分析 → 必读 references/read-analyze.md；图表 → 必读 references/chart-api.md……）。

**模式 2：按领域组织**。多领域技能按领域拆分，避免加载无关内容：

```text
structure-review/
├── SKILL.md（概览与导航）
└── references/
    ├── concrete.md（混凝土构件审查要点）
    ├── steel.md（钢结构审查要点）
    └── foundation.md（地基基础审查要点）
```

用户问钢结构时只读 steel.md。

**模式 3：条件性细节**。基础流程写在正文，高级场景链接出去：「简单编辑直接改；涉及修订追踪，先读 references/redlining.md」。

**硬性要求**：所有参考文件从 SKILL.md 一层直达，不做嵌套引用；超过 100 行的参考文件顶部加目录。

## 技能创建流程

依次执行以下六步，仅在明确不适用时跳过。

**命名规则**：只用小写字母、数字、连字符，不超过 64 字符；目录名与 frontmatter name 保持一致；优先简短、动词引导、描述动作的短语；按软件加前缀可提升触发准确性（如 etabs-report、excel-cleanup）。

### 第 1 步：通过具体示例理解需求

有效的技能来自对具体使用示例的理解。用 `ask_user_question` 向用户澄清（每次 1-4 个问题，先问最重要的）：

- 「这个技能应支持哪些操作？」
- 「请举几个会用到它的具体任务或说法？」
- 「用户说什么话时应该触发它？」
- 「有没有现成的脚本、文档、模板可以纳入？」

存放位置不用问——默认用户技能目录；仅当用户明确指定别处时用 `--path`，并提醒：不在技能根目录下的位置需配置 SKILLS_EXTRA_PATHS 才会被发现。功能范围清楚后即结束本步。

### 第 2 步：规划可复用内容

对每个具体示例分析：从零完成它要做什么 → 反复做这类事时，哪些东西值得沉淀？

- 「旋转 PDF」类请求 → 每次都重写同样的代码 → 沉淀 `scripts/rotate_pdf.py`。
- 「查某软件接口怎么调」类请求 → 每次都重新摸索 API → 沉淀 `references/api-quickref.md`。
- 「出计算书」类请求 → 每次都需要同样的文档骨架 → 沉淀 `assets/report-template.docx`。

产出清单：本技能要包含哪些 scripts / references / assets。

### 第 3 步：初始化

运行骨架生成脚本（默认创建到用户技能目录）：

```text
use_skill('skill-creator', run='scripts/init_skill.py', run_args='<技能名> --resources scripts,references')
```

- `--resources` 按第 2 步清单取 scripts,references,assets 的子集；不需要资源目录就不传。
- 脚本自动做小写连字符规范化，并检查与现有技能重名。
- 输出中包含创建的技能目录绝对路径，后续编辑写入该目录；生成的 SKILL.md 含 TODO 占位与结构选型指导。

### 第 4 步：编辑

先实现资源，再写正文：

1. 制作第 2 步识别的 scripts / references / assets（可能需要向用户索要材料）。**新脚本必须实际运行验证**；相似脚本多时至少验证有代表性的样本。
2. 写 SKILL.md 正文。始终用祈使式；写「对另一个桥接器实例有益且不显而易见」的内容：程序化知识、领域细节、踩坑规避。风格与密度可对照现有技能（如 `use_skill('excel-link')`）。
3. description 是主要触发机制：同时写清功能与触发情境，用「触发条件：1./2./3.」列表列举用户可能的说法与场景（参照本技能自身的 description）。frontmatter 必须包含 name 与 description；可按需补充 allowed-tools、license 与 metadata（预览版用 metadata.beta）。

写盘一律 UTF-8 无 BOM。

### 第 5 步：校验

```text
use_skill('skill-creator', run='scripts/quick_validate.py', run_args='"<技能目录绝对路径>"')
```

校验编码（含 BOM 检测）、frontmatter 格式、必填字段与命名规则；任何会导致技能无法被系统识别的问题都会在此报错。未通过则修复后重跑。

### 第 6 步：迭代

在真实任务上使用 → 记下卡点与低效处 → 更新 SKILL.md 或资源 → 再测。用户刚用完技能时是收集反馈的最好时机。

## 技能测试

桥接器 无子智能体，独立测试由「新会话」承担，分两层：

- **脚本层**：技能内每个脚本用 `use_skill(..., run=...)` 真实运行，确认输出符合预期。
- **整体层**：请用户**新开一个会话**实测，并给出 1-2 条拟用的测试说法——要像真实用户的自然请求（如「帮我把这份 Excel 整理成台账」），而不是指名技能的指令（如「用 xx 技能的第几节处理」）。观察：是否正确触发、流程是否顺畅、产出是否合格。测试请求里不铺垫答案与预期修复；若技能只有被喂了这些上下文才能成功，说明技能本身需要收紧。

测试产生的临时文件及时清理，避免污染下一轮测试。按结果回到第 6 步迭代。

## 修改现有技能

只修改用户技能目录下的技能（内置技能勿动，见「桥接器 环境要点」）。流程：

1. `use_skill('<技能名>')` 读当前正文，参考文档用 `file=` 参数读。
2. 按本指南规范修改，用 python_executor 写回（显式 `encoding="utf-8"`）。
3. 重跑 quick_validate.py；改过 description 时提醒用户观察触发是否符合预期。
